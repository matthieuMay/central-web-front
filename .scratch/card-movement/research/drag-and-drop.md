# React DnD placement and multi-card feasibility

Researched 2026-10-09. Planning evidence only; no dependencies installed or application code changed.

## Decision

Include mouse-only single-card drag and drop in the first version. Use one board-level `DndProvider` with `HTML5Backend`, a `useDrag` source per card, and one `useDrop` target per column's cards region. Keep Chakra rendering and Motion layout animation. Keep ↑/↓ and existing horizontal buttons/keys as independent keyboard alternatives. Defer multi-card dragging: its selection and persistence changes do not fit the user's condition “if possible and don't change all the code”. This is a design recommendation from the evidence below, not a claim that React DnD cannot transport multiple IDs.

## Verified React DnD integration facts

The provider creates/provides the drag-drop manager from a backend factory. One provider around this board is sufficient; do not create a manager per column. [Official DndProvider source](https://github.com/react-dnd/react-dnd/blob/main/packages/react-dnd/src/core/DndProvider.tsx).

`useDrag` returns collected state, source connector and preview connector; `useDrop` returns collected state and target connector. Attach those to real DOM refs in the existing components, retaining Chakra inside the Motion wrapper. Use typed item `{ cardId }`, type `CARD`, typed drop result `{ columnId, position }`; resolve the latest board state at commit. Keep hook factory dependencies current rather than capturing old arrays. [Official useDrag source](https://github.com/react-dnd/react-dnd/blob/main/packages/react-dnd/src/hooks/useDrag/useDrag.ts), [official useDrop source](https://github.com/react-dnd/react-dnd/blob/main/packages/react-dnd/src/hooks/useDrop/useDrop.ts).

The hook specifications expose `canDrag`, `canDrop`, `hover`, `drop`, `end`, and collected state. `item` should contain minimal data, not component references. `end` runs when dragging ends and can inspect the handled drop result. Important: `hover` can run when `canDrop` is false, so it must respect the movement/edit guard too. Use `drop` for the single commit and `end` for cleanup; do not persist from both. [Official hook types](https://github.com/react-dnd/react-dnd/blob/main/packages/react-dnd/src/hooks/types.ts).

The monitor supplies client pointer coordinates. `isOver({ shallow: true })` distinguishes a target from nested targets, and `didDrop()` in a parent's `drop` identifies a child-handled drop. One column target avoids nesting entirely. If implementation chooses card-half targets plus a column fallback, the parent must return without committing when `didDrop()` is true, and child/parent hover indicators must not both activate. [Official monitor types](https://github.com/react-dnd/react-dnd/blob/main/packages/react-dnd/src/types/monitors.ts).

## Precise insertion and cancellation

Recommended algorithm (design inference using monitor coordinates and the documented API position contract):

1. Read only card rectangles inside the hovered cards-list region. Compare pointer `clientY` with the midpoint of each card in visual order. Before the first midpoint means the first gap; after every midpoint means the trailing gap. Use viewport rectangles with client coordinates; do not mix page offsets.
2. Normalize the destination **after removing the dragged card**. Prefer filtering the source ID from both measurement and destination ordering, so the number of remaining midpoints above the pointer is directly the final position. If measuring the original list instead, for a same-column raw gap `g` and original source index `s`, use `g - 1` when `s < g`, otherwise `g`.
3. Validate existing source/destination IDs and integer index within `0..remainingDestination.length` against current board data on commit. Empty column → position `0`. First/last columns are normal DnD targets; only keyboard horizontal adjacency is bounded, never wrapped.
4. If normalized destination/index equals current location, clear preview and issue no request or arrival celebration. For `[A,B,C,D]`, moving B to the original gap before D gives `[A,C,B,D]` and position 2; B after D gives position 3. Gaps immediately before/after B normalize to a no-op.

Hover updates only ephemeral preview state. Do not change query-cache order or send requests while hovering. On accepted drop, call the shared movement action once; its optimistic mutation gives immediate committed placement. Outside drop, Escape cancellation, leaving the target and `end` clear preview; there is no persisted order to undo. A later API failure uses the existing optimistic ledger to remove only that failed change and retain surviving writes. [Existing rollback mechanism](</Users/gaspard/Desktop/3A/DO-IT/Temps 1/Web1/projet-git/central-web-front/src/api/mutations.ts:31>).

Use a stable insertion marker first: an overlay line or reserved gap must not repeatedly move the measured midpoint boundaries and oscillate the chosen gap. A line alone does not shift neighbors; if a local gap reserves space, neighbors can animate while the authoritative board order remains unchanged. Measure stable non-preview wrappers or account for the reserved gap; never count the marker as a card. Disable marker on forbidden/no-op targets.

Keep interactive descendants usable. A small drag handle is the clearest source attachment if whole-card dragging interferes with the pencil or text selection; verify mouse activation before choosing the extra UI. Suppress any trailing drag-click that would toggle selection. Preserve keyboard/form guards, focus the moved card after DOM placement, and recover source focus after rollback. DnD itself is not the keyboard alternative.

## Native preview, Motion and arrival

HTML5 backend registers native drag events and sets a drag image from the preview node, falling back to the source node. Its default delayed dragging-state capture keeps a normal-looking snapshot while the original can be dimmed. Keep the source mounted during hover. This native snapshot is the smallest mouse preview and follows the pointer without adding Motion `drag`. Native preview rendering and cancellation behavior still require browser checks. [Official HTML5 backend source](https://github.com/react-dnd/react-dnd/blob/main/packages/backend-html5/src/HTML5BackendImpl.ts), [official preview options](https://github.com/react-dnd/react-dnd/blob/main/packages/react-dnd/src/types/options.ts).

A custom drag layer is **optional**, justified only if the native snapshot/drop visual fails the continuity requirement in a prototype. React DnD offers `useDragLayer`; HTML5 backend offers an empty image to suppress the native snapshot. A custom layer entails extra positioning/scroll, cleanup and landing coordination; it is not needed for precise placement. [Official useDragLayer source](https://github.com/react-dnd/react-dnd/blob/main/packages/react-dnd/src/hooks/useDragLayer.ts), [official getEmptyImage source](https://github.com/react-dnd/react-dnd/blob/main/packages/backend-html5/src/getEmptyImage.ts).

Motion should own committed layout transitions and marker/opacity transitions; React DnD owns dragging and targeting. Existing `layoutId` bridges cards across column mounts. A rendered custom ghost must not reuse `card-{id}` or card DOM IDs: shared IDs connect elements and simultaneous copies crossfade. Keep the existing board `LayoutGroup`. Use `layoutScroll` only if an actual scroll container is introduced. A native snapshot is outside Motion's projection tree and has no shared-layout identity. This design animates committed placement from the source's prior board position; continuous pointer-to-final-slot travel may require the optional custom layer and must not be promised without browser validation. [Official Motion layout guide](https://motion.dev/docs/react-layout-animations).

The newly requested confetti belongs to the **moved card's visual arrival at any destination**, including same-column reorder, not only the final board column. The user confirmed that the burst occurs on arrival even while persistence remains pending. Coordinate by a movement token and moved card ID; neighbor layout callbacks, mount, refetch and rollback must not trigger it. Use `onLayoutAnimationComplete` for committed card travel, since general `onAnimationComplete` excludes layout animation. Resolve missing/no-distance/reduced-motion completion explicitly, without a guessed timer. Reduced motion should use an accessible arrival message and omit particles/travel. Error clears an unconsumed arrival token and animates the return; a burst already shown before a later failure is not repeated. [Official Motion component callbacks](https://motion.dev/docs/react-motion-component).

## Why defer multi-card dragging

React DnD can carry an item containing multiple IDs; that alone supplies no multi-selection or atomic persistence. This app would need a new selection set, additive selection gesture and accessibility semantics, group ordering rules, grouped preview, multi-card focus rules, adjusted no-op/insertion calculations and coordination across separate requests. Current API documentation exposes a one-card PUT, with no documented atomic group endpoint. Even serial PUTs can partially succeed; rolling back the entire UI would contradict successful server moves. Compensating PUTs can also fail. These are inferences from the cited hook item contract, the single-selection local code and API contract, not verified backend batch guarantees. Defer the bonus unless a later task explicitly supplies those decisions and atomic persistence.
